03

The ledger

Written against the actual code, not in the abstract.

What genuinely gets better
Fuelling gets its context

The thing you asked for. The day cell already holds the athlete, the ISO date and the sessions, so the macro footer is a render change to renderPlanGrid(), not new architecture.

One athlete selector, one week

Today _planAthlete and _nutAthlete are separate variables in separate localStorage keys. A coach can be on Jordan in one tab and Sam in the other with nothing on screen saying so. Merging kills that class of mistake outright.

Training load lands beside the macros

Block view lets Alex set Week 9's calories while looking at "68 km, long 30k". For body composition work against a running block that is the context he is currently missing.

Programme settings go home

Start-date override, programme length and Restart programme currently live in the Nutrition toolbar, which is an accident of build order. They are programme settings and would sit correctly in a Programming tab.

The join already exists

_plannedKmForWeek() already reads planned sessions from inside the nutrition render. The two datasets are joined today. Consolidation is mostly a UI question, not a data one.

What gets worse
Block view runs out of screen

The nutrition row is 11 columns at min-width:780px and already scrolls sideways with a sticky first column. Adding sessions, load and key session makes it 14–15. The mobile breakpoints that remap cells to a stacked card would all need rewriting.

Two coaches, one context

Right now you can sit in Planning on one athlete while Alex sits in Nutrition on another. One tab means one athlete selection per person per view. In a 2:1 model where you split by discipline, this is the sharpest cost.

You lose a badge

tab-planning-count counts this week's sessions; tab-nut-count is its own signal. One tab means one number, so one of those early-warning signals disappears from the nav.

A mode to forget you are in

Week and Block are different enough that landing in the wrong one is disorienting. It needs a loud persistent affordance and per-coach memory of the last view, which is more state, not less.

Real refactor, on fresh code

renderPlanning() and renderNutritionTab() are separate render paths with separate state and separate persistence, and switchTab() has a hardcoded tab list and id map. The sport target columns shipped into that nutrition table on 17 Aug and have not been used in anger yet. This churns days-old code.

What I actually think

The Week view is right and I would build it whatever else you decide. Training and fuelling on the same day column is the correct home for a daily override, and my earlier spec put it in the wrong place by parking the day strip inside the Nutrition week row.

The Block view merge is the part I am not convinced by. It buys Alex one useful column group and costs a table that is already too wide, a badge, and a rewrite of code that shipped last week. You could get most of its value by adding a single Load column to the existing nutrition table and leaving the tabs alone.

But this genuinely turns on how the two of you work, and that is not something I can read out of the repo.

If you mostly work like this Per-athlete deep dive

You open Jordan and work through everything about Jordan — training, fuelling, check-in — then move to the next athlete. Consolidation wins clearly. One tab, one athlete, everything about them in front of you.

Or if you mostly work like this Per-discipline sweep

Alex sits down and does nutrition for all twelve athletes in one pass; you do training for all twelve in another. Consolidation makes both of you wade through the other's context twelve times. Keep the tabs, connect them.
